# Work in a stack

A stack is a chain of branches, each built on the one below, the first on `main`, with one pull request for each. This skill covers what is particular to kb-mcp. For the tool itself, read its own skill if it is installed (`gh skill install github/gh-stack`), or `gh stack <command> --help`.

## Before you start

- `gh stack --help` works. If not, the person installs it: `gh extension install github/gh-stack`.
- Never commit on `main`: it is protected, and takes changes only through pull requests that pass the `check` job.
- Each commit is a conventional commit ending with a full stop (`CONTRIBUTING.md`, Commits). Pull requests merge with a merge commit, so every commit on a branch lands on `main` as written and in the changelog.

## Split by concern

- One concern per branch, readable on its own. A change and the docs that describe it are one concern.
- Order the layers so each builds and passes on its own: kb-core before the tool and the command that use it; a dependency update on its own branch.

## Steps

1. Start the stack: `gh stack init <branch>` from `main`, or `gh stack init <branch1> <branch2>` to adopt branches that exist. Name branches `<type>/<subject>`, such as `feat/kb-links`.
2. Commit the bottom layer, then `gh stack add <next-branch>` for each layer above, committing on each in turn.
3. On each branch, run `just ci`, and `just book-build` if the book changed.
4. Review each layer against the one below: `/kb-mcp-dev:review-code <branch>`, `/kb-mcp-dev:review-docs <branch>`. Fix a finding on the branch it belongs to, then `gh stack rebase --upstack` to carry it up. Record the round in the reviewed branch's log, `.ai/reviews/<kind>/<branch>.md` (`book/src/development/reviewing.md`, "The review log").
5. Show the person `gh stack view` and the commits on each branch (`git log --oneline <base>..<branch>`). Push only when they say so: `gh stack submit` pushes every branch and opens the pull requests, which is visible to others. Run by an agent it opens drafts with generated titles; open each pull request with `gh pr create` and its own title and description first, then `gh stack submit` links them.
6. When `main` moves, `gh stack rebase` carries every layer onto it, locally. `gh stack sync` also pushes every branch, so ask the person before running it. On a conflict, resolve it and run `gh stack rebase --continue`, or `gh stack rebase --abort` to restore the branches.

## Merging

Merging is the person's step, not the agent's, unless they ask. The stack merges from the bottom up. After it merges, `gh stack sync --prune` removes the merged branches; it pushes too, so it is the person's step as well.

## Gotchas

- **The base of a layer** is the branch below it, not `main`: `gh stack view --json` lists the branches bottom to top. `git diff main...<branch>` on an upper layer shows the layers below as well.
- **A fix to a lower layer** goes on that layer's branch. A fix-up commit on a higher branch leaves the lower pull request wrong.
- **An open release PR** is regenerated by every merge to `main`. See `/kb-mcp-dev:release` before merging while one is open.
